# The SAM Coupe Technical Manual as a source, and where it is wrong.
#
#     https://sam.speccy.cz/systech/sam-coupe_tech-man_v3-0.pdf
#
# Not a submodule, because it is a scanned PDF rather than something
# that can be assembled or diffed.  Worth knowing about, because it
# names things neither reference source does: ALLOCT's byte values,
# SLOTT and utility pages, and the ROM vectors.
#
# It confirms, in its own words, things this project had derived:
#
#     CMDADDRT  5BDAH  (2) Start of command address table.
#         which is what INSTALL_EXTENDED_PUT reads to find the ROM's PUT
#     PAGER     5BE0H  (14) Reserved for paging subroutine.
#         fourteen bytes, exactly the block INSTALL_SYSPAGE_CODE fills
#     INSLV     (2) Block move vector.
#         which the ROM source only showed by how STRMOV1 uses it
#     DOSFLG    5BC2H  Zero if no DOS loaded, else page number
#     DOSCNT    5BC3H  Bit 0 is set if DOS is in control
#
# THE PALETTE BYTE, confirmed against MasterBASIC's own arithmetic.
#
# The manual's layout is GRBbGRB: bits 6, 5 and 4 the high bit of green,
# red and blue, bits 2, 1 and 0 the low bit of the same three, and bit 3
# the least significant bit of ALL THREE at once.  So a channel is
# 4*high + 2*low + bright, a value from 0 to 7, and "bright" is not a
# flag on top of a colour -- it is the bottom bit of the colour.
#
# PALETTE_INTENSITY at MB &6AC3 is independent evidence for that reading.
# It works out 4*green + 2*red + 1*blue, and the constant it adds for
# bit 3 is 7 -- which is 4 + 2 + 1, the sum of the three weights, and is
# the right constant only if that bit is worth one in every channel.
# Run the ROM's sixteen starting colours through the channel arithmetic
# and through those eight instructions and they agree on all sixteen.
#
# It also explains the ROM's own table: plain white is &78 and not &70
# because it wants 5 of 7 in each channel, and bright white &7F wants 7.
# Bit 3 is set for white and for nothing else in that table.

# KNOWN TYPOS.  Online copies carry errors; these are the ones met so
# far, all in the system variable tables.
#
#   INSLV is given as "BBBAH".  It is 5BBAH -- the entry sits between
#   OVERF at 5BB9H and STRLOCN at 5BBCH, and is two bytes.
#
#   5AFAH is MTOFCV in the table and MTOKV in the prose that describes
#   it.  This project uses MTOKV.
#
#   DKDEF is given as 5BDCH, which is also MNOP's address.  It belongs
#   at 5BCEH, between FPSBOT at 5BCAH and DKLIM at 5BD0H.
#
#   BSTKEND and BASSTK are both given as 5BC4H.
#
#   In the 5C4FH-5C56H run the descriptions are shifted from the names
#   by two rows: CURCHL is described as "number of line with > cursor",
#   DEFADD as "start of channels area", and so on.
#
#   In the floating point calculator table: SQN for SGN at &42, SOR for
#   SQR at &43, JFFALSE for JPFALSE at &1F, and "SWOp13" with a lower
#   case p at &1C.  &0F is given as NOTE where the string series has
#   SNOTE for the same comparison, so the numeric name looks a letter
#   short, though that one is a guess.
#
# WHAT IT CONFIRMED.  The calculator section was read against
# tools/fpcalc.py, which takes its table from ref/samrom/fpcmain.asm.
# Every code that eats bytes of its own agrees: JPTRUE, JPFALSE, JUMP
# and LDBREG take one, ONELIT one, FIVELIT five, LKADDRB and LKADDRW two,
# and SOMELIT a count byte followed by that many.  DUP and SWOP13 take
# none, which is what makes the RST FPCALC list at &7271 end where the
# listing says it does -- the point the CALL &50D7 question turned on.
#
# The ROM source is much the fuller of the two: 150 codes against the
# manual's 74, and the only code the manual had that the project did not
# was &00 MULT, dropped by a regex that wanted leading whitespace on a
# line the table's own label begins.  Fixed.
#
# Two more confirmations, both of readings this project had made from
# the code alone:
#
#   DEVICE 5A73H "0=upper window, 1=lower window, 2=printer, 3=other",
#   which is what makes CLAMP_CHAR_HEIGHT clamping to 4 when DEVICE is 1
#   a height limit for a four-line window rather than anything to do
#   with streams.
#
#   "The 69 keys and 4 shift states give 276 key [positions] in a
#   keyboard 'map'", with KEY Posn,x taking 0-275.  So KTAB runs
#   &58E0-&59F3, which contains every entry this image pokes -- 97 and
#   106 from INSTALL_SYSPAGE_CODE, 255 and 264 from the installer -- and
#   explains why vars.asm names nothing between KTAB and &5A00.
#
# So: read it for the names and the prose, and check any address in it
# against ref/samrom/vars.asm before relying on it.
