# The SAM Coupe Technical Manual as a source, and where it is wrong.
#
#     https://sam.speccy.cz/systech/sam-coupe_tech-man_v3-0.pdf
#
# The scanned PDF is at the address above.  A transcription of the same
# manual is a submodule -- ref/sam-coupe-technical-manual -- and having
# both matters: where they differ, the difference is the PDF's copy and
# not the manual's, which is what the typo list below turns on.
#
# Worth knowing about, because it names things neither reference source
# does: ALLOCT's byte values, SLOTT and utility pages, and the ROM
# vectors.
#
# It confirms, in its own words, things this project had derived:
#
#     CMDADDRT  5BDAH  (2) Start of command address table.
#         which is what INSTALL_EXTENDED_PUT reads to find the ROM's PUT
#     PAGER     5BE0H  (14) Reserved for paging subroutine.
#         fourteen bytes, exactly the block INSTALL_SYSPAGE_CODE fills
#     INSLV     (2) Block move vector.
#         which the ROM source only showed by how STRMOV1 uses it
#     DOSFLG    5BC2H  Zero if no DOS loaded, else page number
#     DOSCNT    5BC3H  Bit 0 is set if DOS is in control
#
# THE PALETTE BYTE, confirmed against MasterBASIC's own arithmetic.
#
# The manual's layout is GRBbGRB: bits 6, 5 and 4 the high bit of green,
# red and blue, bits 2, 1 and 0 the low bit of the same three, and bit 3
# the least significant bit of ALL THREE at once.  So a channel is
# 4*high + 2*low + bright, a value from 0 to 7, and "bright" is not a
# flag on top of a colour -- it is the bottom bit of the colour.
#
# PALETTE_INTENSITY at MB &6AC3 is independent evidence for that reading.
# It works out 4*green + 2*red + 1*blue, and the constant it adds for
# bit 3 is 7 -- which is 4 + 2 + 1, the sum of the three weights, and is
# the right constant only if that bit is worth one in every channel.
# Run the ROM's sixteen starting colours through the channel arithmetic
# and through those eight instructions and they agree on all sixteen.
#
# It also explains the ROM's own table: plain white is &78 and not &70
# because it wants 5 of 7 in each channel, and bright white &7F wants 7.
# Bit 3 is set for white and for nothing else in that table.

# KNOWN TYPOS, CHECKED AGAINST A SECOND TRANSCRIPTION.
#
# ref/sam-coupe-technical-manual is Stefan Drissen's transcription of the
# same manual, and running the list past it splits it in two: errors the
# online PDF introduced, which are gone there, and errors the manual
# itself has, which are in both.  Every address below was then checked
# against ref/samrom/vars.asm, which settles it either way.
#
# THE PDF'S OWN, all five confirmed absent from the transcription:
#
#   INSLV given as "BBBAH".  The transcription has 5BBA, between OVERF
#   at 5BB9 and STRLOCN at 5BBC, and vars.asm has INSLV at VAR2+&01BA.
#
#   5AFAH as MTOFCV in the table and MTOKV in the prose.  The
#   transcription says MTOKV in both, which is what this project uses.
#
#   DKDEF given as 5BDCH, MNOP's address.  The transcription has DKDEF
#   at 5BCE and MNOP at 5BDC, and vars.asm has DKDEF at VAR2+&01CE.
#   The derivation that put it at 5BCEH was right, but the neighbour it
#   named was not: FPSBOT is 5BCC, not 5BCA.  Corrected here.
#
#   BSTKEND and BASSTK both given as 5BC4H.  They are 5BC4 and 5BC6, in
#   the transcription and in vars.asm alike.
#
#   The 5C4FH-5C56H run with its descriptions shifted two rows.  The
#   transcription has them lined up -- CHANS 5C4F "start of channels
#   area", CURCHL 5C51 "start of current channel", and the "number of
#   line with > cursor" back on EPPC at 5C49 where it belongs.
#
# AND FOUR IN THE CALCULATOR TABLE, where the split runs the other way.
#
#   JFFALSE for JPFALSE at &1F, and "SWOp13" with a lower case p at
#   &1C, are the PDF's: the transcription has both right.
#
#   SQN for SGN at &42 and SOR for SQR at &43 are the manual's own --
#   both transcriptions carry them.  The manual contradicts itself,
#   which is how they are known to be slips: its token table gives SGN
#   and SQR a few pages later, and fpcmain.asm has SGN at &42 and SQR
#   at &43.
#
#   &0F as NOTE is the manual's own too, and the guess that it was a
#   letter short is now settled: fpcmain.asm calls it NNOTE, N<>N,
#   against SNOTE at &16 for $<>$.  The whole series is paired that way
#   -- NLESE/SLESE, NGRTE/SGRTE, NLESS/SLESS, NEQUAL/SEQUAL,
#   NGRTR/SGRTR -- so NOTE is the only one in the manual missing its N.
#
# FOUR ERRORS IN THE TRANSCRIPTION ITSELF, found by checking that the
# system variable table runs in increasing address order.  It does,
# everywhere but here, and each of the four is confirmed three ways: by
# the ordering, by the byte counts of the rows around it, and by
# ref/samrom/vars.asm.
#
#   OVERT     5353  should be 5A53, between M23INKT 5A52 and INVERT 5A54
#   Reserved  5371  should be 5A71 -- PRPOSN at 5A70 is two bytes, and
#                   vars.asm calls the second "1 BYTE EXTRA FOR
#                   CONVENIENT LD", which is what Reserved means here
#   TEMPW1    53C8  should be 5AC8, with TEMPW2 at 5ACA and TEMPW3 5ACC
#   LSPTR     5B8E  should be 5B8B.  AUTOSTEP at 5B89 is two bytes, LSPTR
#                   is two more, LNPTR follows at 5B8D -- and 5B8E is
#                   MSEDP's, so the file gives one address to two names
#
# The first three are one OCR substitution made three times, 5A read as
# 53, and the project's README says OCR errors are in scope to fix.  The
# fourth could be either the scan's or the manual's; without the scan
# there is no telling, and it is wrong in the file either way.
#
# Not errors, though both look like one against vars.asm:
#
#   SLDEV at 5A06.  vars.asm has PSLD there and its own SLDEV at 5BB7,
#   both described "DEVICE LETTER/NUMBER".  Two sources naming the same
#   pair of bytes differently, not a mistake in either.
#
#   STREAMS at 5C0C with 42 bytes.  vars.asm puts the label at 5C10 and
#   then says in its own comment "USES 5C0C-5C35 FOR STREAMS -5 TO 15",
#   so the manual has the table's base and vars.asm an offset into it.
#   21 streams of two bytes is the 42, and 5C0C + &2A is CHARS at 5C36.

# WHAT IT CONFIRMED.  The calculator section was read against
# tools/fpcalc.py, which takes its table from ref/samrom/fpcmain.asm.
# Every code that eats bytes of its own agrees: JPTRUE, JPFALSE, JUMP
# and LDBREG take one, ONELIT one, FIVELIT five, LKADDRB and LKADDRW two,
# and SOMELIT a count byte followed by that many.  DUP and SWOP13 take
# none, which is what makes the RST FPCALC list at &7271 end where the
# listing says it does -- the point the CALL &50D7 question turned on.
#
# The ROM source is much the fuller of the two: 150 codes against the
# manual's 74, and the only code the manual had that the project did not
# was &00 MULT, dropped by a regex that wanted leading whitespace on a
# line the table's own label begins.  Fixed.
#
# Two more confirmations, both of readings this project had made from
# the code alone:
#
#   DEVICE 5A73H "0=upper window, 1=lower window, 2=printer, 3=other",
#   which is what makes CLAMP_CHAR_HEIGHT clamping to 4 when DEVICE is 1
#   a height limit for a four-line window rather than anything to do
#   with streams.
#
#   "The 69 keys and 4 shift states give 276 key [positions] in a
#   keyboard 'map'", with KEY Posn,x taking 0-275.  So KTAB runs
#   &58E0-&59F3, which contains every entry this image pokes -- 97 and
#   106 from INSTALL_SYSPAGE_CODE, 255 and 264 from the installer -- and
#   explains why vars.asm names nothing between KTAB and &5A00.
#
# So: read it for the names and the prose, and check any address in it
# against ref/samrom/vars.asm before relying on it.
