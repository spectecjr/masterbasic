# The LOAD and SAVE hooks as MasterBASIC rewrote them: where the
# compressed-file paths branch off.
#
# Prose for listings/clean/ only.

DOC HOOK_HSAVE
    Hook 132: save the file whose header the ROM has built.

    MASTERDOS'S VERSION SAVED THE BLOCK AND CLOSED THE MAP.  This one
    does that too -- DSVBL then CFSM, at HOOK_HSAVE_4 -- but only for a
    BASIC program, or when CMPFG is zero because SAVE MODE 1 or no
    SAVE MODE at all is in force.  The manual's "no attempt is made to
    compress BASIC programs" is the CP against &10.

    ANYTHING ELSE IS HANDED TO MASTERBASIC.  Bit 2 of the flags byte in
    the entry -- offset 220, which is IX+&EF once the entry sits at
    FFSA in DCHAN -- is set to say the file is compressed, and then:

        SCREEN$ with CMPFG 2       SAVE MODE 3.  Bit 3 of the same byte
                                   is set as well, the byte after it is
                                   taken in A, and COMPRESS_SCREEN_FILE
                                   does the work
        everything else            COMPRESS_FILE, with the start in HL
                                   -- its page already in the window
                                   from &64E8 -- the length's whole
                                   pages in A and its remainder in DE

    Both come back to SCFSM, which closes the map as CFSM does.

    THE THREE BYTES AT OFFSET 229 are written on the SAVE MODE 3 path
    only, and they are the compressed length.  FPTR gives the position
    in the file once the compressor has written it -- sectors times
    510 plus the offset -- and nine off that is the data without its
    header, put into page form and stored through IX at &F8.  That is
    the writer docs/evidence-wanted.md item 8 could not find by name:
    entry offset 229 is ROM header offset 24, and nothing writes
    DIFA+24 because the write goes through the entry in DCHAN.
    HOOK_HLOAD_1 reads the three bytes back from STR-11, and
    MasterBASIC's &62A6 turns them back into a byte count in EXPAND_INPUT_POINTER,
    which LOAD_NEXT_INPUT_BLOCK counts down as it refills the input.
    Two edges of it: the count takes in the three &FF bytes the
    compressor closes the stream with, which the expander skips, and
    &62AF keeps only HL of the folded length -- a screen never needs
    more, but the field is not general.

DOS &64E0 : the caller's window, put back at HSAVE1
DOS &64E5 : the start page, out of the ROM's header
DOS &64F0 : the nine-byte header goes out first, and into the entry at offset 211
DOS &64FA : SAVE MODE less one, as MasterBASIC's SET_COMPRESSION_MODE left it
DOS &64FE : zero is no compression: the plain save
DOS &6501 expr FFSA
DOS &6501 : the type, from the entry in DCHAN
DOS &6504 expr TYPE_BASIC
DOS &6506 : a BASIC program is never compressed
DOS &650B expr FFSA+DIR_FLAGS
DOS &650B : the entry's flags byte, offset 220
DOS &650F : bit 2: the file is compressed
DOS &6512 expr TYPE_SCREEN
DOS &6514 : not a screen, so the general compressor
DOS &6519 : CMPFG 1 is SAVE MODE 2, and takes the general compressor too
DOS &6529 : bit 3: a SAVE MODE 3 screen
DOS &652C : the byte after the flags, offset 221
DOS &6535 : less the nine-byte header
DOS &6540 : IX+&F8 is entry offset 229
DOS &6544 : the pages, then the rest: the compressed length in page form

DOS &6360 : JR IF A SENSIBLE TAPE SPEED WAS SPECIFIED -- the author's "JR IF NO SENSIBLE TAPE SPEED" has it backwards

DOC DDEL
    Wait DWAI+1 quarter-seconds before writing -- the INC A at &6566,
    and DWAI's own declaration says it is stored one less than the
    count -- so that a drive which has just been started has come up
    to speed.  RAM discs skip it.

# Not SVHD1's end -- that RETs at &5F4C -- but a routine of its own, not
# in the 1991 source, reached only by READ_SAVED_SECTOR's JP at &663A.
DOS &5F4D SKIP_FILE_HEADER
    Read and discard the nine bytes of the file header, through LBYT,
    once the sector holding it has been read.

# LDBLK's whole-sector loop.  The annotated source's "LDBLK -- load a
# block from the open file" banner had landed here, on the loop, rather
# than on the entry at &4856.
DOC LDB3
    The whole-sector loop of LDBLK: while a full sector's worth is still
    wanted, read the next sector straight to the caller's address -- a
    RAM disc through RDLB, a floppy through LDB4 -- and go round.  With
    less than a sector left, LDB3_2 reads it into the buffer and jumps
    back into LDBLK to copy the tail.

DOS &4897 : 510 bytes or fewer left: read it into the buffer and copy the tail through LDBLK_1

# AUTNAM is a parameter block; tools/dis_mb.py declares it data before
# the sweeps run, and this says what is in it.
DOS &65D5 : the twenty-eight bytes AUINSR copies over DSTR1, laid out as the source declares that block: drive 1, &FF in FSTR1 and SSTR1, "D" in LSTR1, &10 in NSTR1, the name AUTO* padded to the fourteen of the name field, a zero in HD001, and &FFFF over the three header words and the page pair

DOS &7862 OPEN_BASIC_FOR_MERGE

DOC OPEN_BASIC_FOR_MERGE
     PART HOOKS -- Extending BASIC, the new functions, and the ROM patches

    The DOS's half of MERGE *: find the named BASIC program, open it,
    and hand MasterBASIC what it needs to splice the lines in.

    NO CALLER IN THIS HALF -- MasterBASIC's CMD_MERGE reaches it through
    CALLDOS.  The name has already been evaluated; this insists on a
    disc, wants a BASIC file, finds it, and reads three bytes at entry
    offset 221: the ROM header's offset 16, where SAVE put the length
    of the program's lines alone, NVARS less PROG in page form.  Then
    the first sector is read and the first two bytes after the nine-
    byte header -- the first line number, high byte first as a program
    stores it -- come back in BC, with the length in A and HL for
    CMD_MERGE to make room by.

DOS &7865 expr TYPE_BASIC
DOS &7870 : offset 221: header offset 16, the length of the program's lines in page form
DOS &787E : DRAM+9, the first line number of the program, high byte first

DOC HOOK_HLOAD
    Hook 130: load the body of a file the header hook has opened.

    MASTERDOS'S HLOAD WAS FOUR INSTRUCTIONS -- NETPA, DSCHD, LDBLK --
    and this one branches first on two bits of ENTRY_FLAGS, the copy of the
    entry's flags byte that COPY_HEADER_FIELDS left there -- LOAD by
    number writes it in CHECK_FILE_TYPE first, but that ends in JR
    GTFL4 and reaches the same copy:

        bit 2 clear      not compressed: the plain load, with the
                         BASIC-program case below
        bit 2 set        compressed: EXPAND_FILE in the other half,
                         given the type in C
        bits 2 and 3     a SAVE MODE 3 screen: the expander at &62A6,
                         given the compressed length from STR-11, in
                         page form, and the byte after the flags in A

    Every path ends in HOOK_SKSAFE, which parks the head.

    THE BASIC-PROGRAM CASE on the plain path: when the type is BASIC
    and the command is LOAD, the byte at DRAM+9 is written into the
    system page at &4A97 -- the operand of the LD (HL),&00 in the stub
    the boot put at &4A84, which CMDBUF_PROLOGUE runs to plant that
    byte at the start of the program -- and DRAM+9 is then set to
    &FF.  DRAM+9 is the first
    byte of the program as it will be loaded, the high byte of its
    first line number, and &FF there is the ROM's end-of-program
    stopper: the program loads invisible, and stays so until the stub
    at &4A84 puts the saved byte back at (PROG).  DLVM2 at &606F
    arranges that by sending the ROM's LOAD back through that stub.
    What the byte at &4A97 means is worked out in notes/mb-cmdbuf.txt
    from the other side.

DOS &642E : bit 2 of the flags: the file is compressed
DOS &6432 : bit 3: a SAVE MODE 3 screen
DOS &6439 expr FFSA
DOS &6439 : the type, for the expander
DOS &6443 : the byte after the flags, offset 221
DOS &6449 : STR-11, where COPY_HEADER_FIELDS lands entry offset 229: the compressed length's page
DOS &644D : STR-10, offsets 230 and 231: the address half of the compressed length, whose page is the byte above
DOS &645F expr TYPE_BASIC
DOS &6468 : the LOAD token: not MERGE, not VERIFY
DOS &646C : DRAM+9, the byte after the nine-byte header in the first sector
DOS &6474 : &FF, the ROM's end-of-program stopper, so the program loads invisible until the stub at &4A84 puts the saved byte back

# PART C11's entries that had no banner of this project's own.

DOC HOOK_HLDBK
    Hook 161, load a block: the dispatcher has swapped the register
    sets, so this swaps them back and stores A as PGES1 before LDBLK.
    HLDBK_NO_EXX below is the same entry for a caller that did not
    come through the dispatcher.

DOC HOOK_HKSB
    Hook 150, save a block: the same swap-back and PGES1 store, then
    HSVBK's quarter-second delay and the HSVB2 loop.

DOC DSVBL
    SVBLK after DDEL's quarter-second wait, for a save that does not
    follow another write and must let the drive come up to speed.

DOC SVBSI
    The tail of a save whose data ended inside the buffer: GRPNT to
    the buffer pointer, then SVBS1 pads to the end.

DOC SVBS1
    Pad the rest of the sector: while the pointer is short of the 512,
    SVBS2 writes a zero and steps on; at the end SVBS3 fetches the
    track and sector and returns with carry set, the source's "single
    sector".

DOC SVBS2
    One zero into the buffer and on to the next byte, without moving
    RPT.
