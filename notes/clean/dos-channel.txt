DOC GTBUF
    Point HL at the sector buffer for the channel in IX.

    IX ADDRESSES THE DISK CHANNEL RECORD, and it does so through most of
    the disk code, which is why so much of it reads as an offset from
    nothing in particular.  The record is DCHAN, at &7C00, and the
    listing has a label on each of its fields:

        DCHAN+0   SVBC    saved BC
        DCHAN+2   SVDE    saved DE, usually a track and sector
        DCHAN+4   RFDH    the directory scan mode
        DCHAN+5   SVHL    saved HL, usually the transfer address
        DCHAN+7   SVIX    saved IX
        DCHAN+9   REG1    scratch
        DCHAN+11  DRIVE   which drive this channel is on
        DCHAN+12  FLAG3   the flag byte, whose bits are set out at &7C0C.
                          "The sector has been written to" is bit 3 of the
                          same offset in an open file's channel record --
                          &457B, &6F62, &6FD5 -- not of DCHAN's
        DCHAN+13  RPT     how far through the buffer the file has read
        DCHAN+15  BUF     where the buffer is
        DCHAN+17  NSR     the track and sector this buffer holds
        DCHAN+19  FSA     a 256-byte image of the directory entry

    So a displacement here is written as the field minus the base, which
    says which field it is rather than how far along it sits.

DOC TIRD
    Which kind of drive is this channel on?

    Drives 1 and 2 are floppies and anything from 3 to 7 is a RAM disc,
    so one compare answers it: carry set for a real drive, clear for a
    RAM disc.  Every transfer asks this before it does anything else,
    and the RAM disc paths divert on the answer without ever reaching a
    controller.

DOS &615A : the drive this channel is on
DOS &615F : carry for a floppy, no carry for a RAM disc

DOC TIRDXDCT
    The same question, with the failure count cleared first.

    The two are one routine with two doors: a caller starting a fresh
    transfer comes in at the top so that the ten attempts CDE1 allows are
    counted from zero, and one only asking what kind of drive it has
    comes in below.

DOC D510
    ENTRY: BHL=24-BIT NUMBER
    EXIT: HL=NUMBER MOD 510, HL'=NUMBER DIV 510 + 1 (1 = first sector);
    a nonzero exact multiple of 510 comes back as HL=510 with HL' one
    lower, so a pointer at a sector's end stays in that sector -- the
    "buffer full" form AT_SECTOR_LINK tests for.  The tail from &71C4
    that does that is not in the 1991 source.
    Division by repeated subtraction, which is cheap here because a
    file's sector count is small; HL' is counted before each SBC,
    including the one that fails, which is what makes it one-based.

DOS &71D3 : HL=510 and HL' one less: the pointer stays at the end of its sector.  The author's "HL=SECTOR" is wrong on the instruction he wrote it for as well -- HL is the displacement on every exit

EQU NTRK : offset 785 in a channel record: WRRAM + 510, the first link byte of the record's own sector buffer.  Not a track count

DOC INPST
    INP$(#stream, n) -- n characters from a stream, or a whole line.

    THE ZERO IS THE EXTENSION, and it is why this routine no longer
    matches stock MasterDOS 2.3.  There, a count of zero was rejected:
    DEC BC made it &FFFF, B came out &40 or more, and the range check
    reported "integer out of range".  Here the count is tested first and
    zero takes a path of its own.

    WHAT THAT PATH DOES is arrange for the read loop to stop at a
    carriage return instead of at a count.  Zero is decremented to &FFFF
    and that is what goes on the stack as the count, while BC is brought
    back up to one for the workspace claim -- one byte, because the
    length is not known yet.  In the loop, INC B on a B of &FF gives
    zero, which is the branch that tests for &0D; any real count leaves B
    non-zero and skips it.  So &FFFF is not a number of characters at
    all, it is the marker for "until the line ends".

    The manual: "you can use a special value of zero in place of the
    number of characters.  This reads in all characters until a carriage
    return is found, like INPUT ... it does not clear the lower part of
    the screen, it does not beep with each input character, and it is
    much faster than INPUT."

    THE RANGE CHECK ALSO MOVED.  Stock made it before opening the
    stream; here it happens after, because the zero test has to come
    first.  A count above &4000 is still refused: the CP &40 sees the
    count less one, so &4000 itself passes and &4001 is the first
    refused, in stock and here alike.

DOS &7A11 : "#" introduces the stream
DOS &7A19 : sixteen less the stream: 0 to 16 pass, and 17 up is "Invalid stream"
DOS &7A69 : a carriage return ends INP$(#s,0)
DOS &7A76 : one more byte of workspace
DOS &7A35 : is a count given at all?
DOS &7A3A : one off, for the range check below; the zero case went to INPST_1 at &7A37, so the author's "Z->FFFF" belongs to the DEC at &7A43 in this build

DOS &7A46 : the count again, or that one byte
