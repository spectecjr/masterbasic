     The part is a mixture because the addresses are: what it holds is
     everything MasterDOS added after the SAMDOS core it grew out of,
     laid down in the order it was written.

     MOVE a TO b -- the general copier.

    EITHER END CAN BE ANYTHING the machine can read or write: a stream
    (`#n`), a device letter ("s:" for the screen, "p:" for the printer,
    "k:" for the keyboard, "d:" for a disc file), or a file.  MOVE does
    not care which, because it does not do the reading and writing
    itself -- it opens a channel at each end and works through the ROM's
    channel machinery, which is what makes one command serve every
    combination.

    THE ACCESS MODE FOR EACH END GOES IN FSTR1 FIRST -- MIN, the ZX IN
    token, for the end being read, MOUT for the end being written.  They
    are access modes and have nothing to do with a serial port, whatever
    an earlier reading of this said; OPMOV reads FSTR1 to decide which.

    AN END THAT NAMES A FILE gets a temporary disc channel, marked by a
    channel letter of "D" with bit 7 set so that the reclaim pass can
    find it afterwards.  An end that names a stream uses that stream's
    existing channel and is not closed with the other.  The two
    parameter blocks the DOS keeps for this sort of thing are swapped by
    EXDAT so that one routine can open either.

    THE WHOLE COMMAND RUNS WITH HMPR ZERO, which is why the operands in
    it read as ROM system variables through the window.  CURCHL, the
    ROM's "which channel am I talking to" pointer, is written before
    every single character; CHANS is where the channel records live.

    Flag 2 is raised to say a MOVE is running; the open and end-of-file
    code reads it, to tell a MOVE from a command that would report "end
    of file".  The directory search reuses the same bit as "a search is
    under way" -- STFPL sets it, SNDFL and REFBUF test it -- but MOVE's
    name evaluation is over before this SETF2, so the two never meet.

DOS &679C : "," or
DOS &67A0 : "TO" between the two
DOS &67A5 : the second name goes in the other parameter block
DOS &67B1 : which command this is, for the end-of-file code to read
DOS &67B5 : the ROM's system page into the window, for the whole command
DOS &67B7 : the code that marks a channel as one to read from
DOS &67BC : open it
DOS &67CB : and the code for one to write to
DOS &67D7 : the second open is an ordinary one, whatever the first was
DOS &67D9 : open that too
DOS &67DC : both open, so the copying can start

DOC OPMV1
    Not a stream, so a file: open a temporary disc channel for it.

    The device letter has to be "D".  RESET_CHANNEL_SCAN walks the
    channel list with the system page in the window and comes back
    with IX on the new record there, so &C000 -- minus &4000 -- puts
    that address into the ROM's own numbering, which is what the
    caller's NSTR1 wants.  The 1 before the INC is a way of setting
    NZ without a compare: an error from here is never "stream not
    open", and OPMOV's callers read Z as exactly that.

DOS &698A expr CASE_BLIND
DOS &698C : "D": only a disc file can be opened here
DOS &6997 : 1, so that the INC leaves NZ: not a stream, so not "stream not open"
DOS &69A1 : minus &4000: the record's window address, into the ROM's numbering

DOS &6D0F expr FFSA+DIR_FLAGS
DOS &6D0F : offset 220 of the destination's entry
DOS &6D17 : &40 on the high byte: NSTR2 holds the source channel in the ROM's numbering, and &4000 puts it in the window; C is still &EF
DOS &6D1A : thirty-six bytes, 220 to 255: the ROM header's tail and the DOS's own bytes after it

DOC MOVA
    Copy, with one special case that makes MOVE more than a copier.

    A DISC FILE MOVED TO THE SCREEN, PRINTER OR KEYBOARD IS LISTED, not
    copied byte for byte.  That is what TOSCQ asks, and it is the reason
    MOVE "d:PROG" TO "s:" shows you a program rather than a screenful of
    tokens.

    THE NINE-BYTE HEADER GOES FIRST, discarded by reading and dropping
    nine characters -- there is no seek on a channel, so skipping is
    reading.  Then, for a BASIC program only, each line is taken apart:
    the line number is printed as a number, the two-byte length is
    dropped, and the text is passed through with INQUFG cleared so that
    the ROM expands the tokens as it prints them.  A five-byte number
    embedded in a line -- the &0E form -- is dropped, because the digits
    that precede it are what the reader wants to see.

    ANY OTHER TYPE goes through MOVCD, a character at a time through
    PRINTABLE_FORM -- the author's "SUPPRESS UNPRINTABLES": control
    codes become the substitute character, and bytes of &80 and up are
    stripped or inverted unless MSFLG lets them through, &FF excepted.
    Only an open-type file, through MOVE1, is copied byte for byte.

    A file with type &0A, an open-type file, is copied and not listed:
    it has no header to skip.

DOS &6864 : and the five bytes after it are dropped; the digits before it have already gone out

DOS &6BE4 : ADDR OF CHANS TERMINATOR, or of the last reserved block if one was seen

DOC MOVJ
    Read B characters and throw them away.

    There is no seek on a channel, so this is what skipping is.

DOC MEOF
    Both ends closed, and the flags cleared.

    CLMOV is called twice with the parameter blocks swapped between, so
    the one routine closes whichever end is in the first block.

DOS &689C : nothing of this command's flags outlives it
DOS &689F : the first end
DOS &68A5 : and then the other

DOC FIRST_DISC_CHANNEL
    Walk the ROM's channel list looking for the DOS's own channels.

    CHANS points at the list, and &401E steps past two things at once:
    the &4000 window bias, and the thirty bytes of the six five-byte
    standard channels the ROM installs.  It is added exactly once.
    Every step after that comes from the record's own length at +9,
    which is what the comment further down says; a &0D where the next
    record's first byte would be is the end of the list -- that is the
    ROM's marker, not the DOS's.

    A channel whose LETTER is "D" with bit 7 set is one of MOVE's own,
    left over from a command that did not finish, and it is reclaimed
    rather than walked past.  The letter is at offset 4 -- the fifth
    byte of the ROM's header, after the output and input routines --
    and RES 5 first folds "d" onto "D".

DOS &68AB : the head of the ROM's channel list

# file being listed, a routine of its own and not MOVJ's loop.
DOS &687C MOVCD
DOS &68AF : one record's worth
DOS &68B7 : a carriage return is the end of the list
DOS &68BA : offset 4 of a ROM channel record is its letter
DOS &68BD : and clearing bit 5 makes "d" match "D"
DOS &68BF : one of MOVE's own, left behind
DOS &68C3 : so reclaim it and start again
DOS &68D2 : otherwise the record says how far to the next

DOC PRINTABLE_FORM
    Make a character safe to print, and say whether to invert it.

    Two DOS variables decide, and both can be poked:

        MSFLG   DVAR 24.  Zero means a character above 127 is printed
                inverse; anything else means it is passed through, and
                only &FF is replaced
        MSUPC   DVAR 25.  What to print instead of a control code, or
                of &FF.  Normally "."

    B comes back as the value for INVERT -- &FF for inverse, zero for
    normal -- and A as the character to print.  The caller writes B into
    the ROM's INVERT and clears it again afterwards, so one character
    comes out inverse rather than everything after it.

DOS &68DA : normal, unless something below says otherwise
DOS &68DC : is this character above 127?
DOS &68E1 : and does MSFLG want those inverted?
DOS &68E8 : if not, only &FF is replaced
DOS &68ED : inverse, and the low seven bits are what is printed
DOS &68EF : the character without its top bit
DOS &68F1 : anything from a space up prints as itself
DOS &68F4 : a control code prints as MSUPC instead

DOC TOSCQ
    Is this a disc file being moved to something that shows it?

    The two channels' device letters answer it.  The source must be "D"
    with bit 7 set -- a temporary channel MOVE made for a named file,
    not a stream already open to a disc file, whose letter is a plain
    "D" -- and the destination one of "S", "P" or "K" -- screen,
    printer or keyboard.  D also comes back
    holding the source file's type, which is what MOVA branches on next.

DOS &68F8 : the channel being read from
DOS &68FB : four bytes into its record is the device letter
DOS &6900 : "D" with bit 7 set: a disc file
DOS &6902 : anything else is copied rather than listed
DOS &6903 : and the type byte is fifteen further on
DOS &6908 : now the channel being written to
DOS &6910 : the screen
DOS &6913 : the printer
DOS &6916 : or the keyboard

DOC MOVRC
    One character in, through the channel's own input routine.

    CURCHL is set to the channel being read, and the address two bytes
    into its record is where the ROM keeps that channel's input routine.
    A high byte of &4B -- the stubs the boot plants at &4BA0 and &4BA9
    in the system page, whose addresses MTBLS puts in the record --
    means the DOS's own, and is called directly; anything else is the
    ROM's, and is reached through CMR with the address planted in the
    instruction that calls it.

DOS &6919 : the channel being read from
DOS &691C : which is where the ROM will read from
DOS &6922 : the input routine is the word at offset 2
DOS &692B : an address of &4Bxx is one of the DOS's own two stubs at &4BA0 and &4BA9
DOS &692F : anything else is the ROM's, so plant the address and call it

DOC MOVWC
    One character out, the same way round.

    The output routine is the word at offset 0 of the record, where the
    input routine's is at 2, so the high byte read to tell whose it is
    comes from one byte in rather than three; the same &4B marks the
    DOS's own.

DOS &6940 : the channel being written to
DOS &6946 : the output routine is the word at offset 0, and only its high byte is wanted
DOS &694C : &4Bxx again, so the DOS writes it as a file
DOS &694F : then write it as a file
DOS &6952 : otherwise let the ROM print it

DOC MOVRC2
    Read one character from the current channel, for MOVE's source:
    the channel's input routine, the word at offset 2, is fetched
    through the window, and an address in the &4Bxx page is one of the
    DOS's own two stubs -- so the DOS reads it itself at DOSIP -- while
    anything else is the ROM's and is planted in the CALL at MTARG.

DOC EVMOV
    Either MOVE operand -- CMD_MOVE calls it for the first before it
    looks for the TO, and again for the second: "#" makes it a stream,
    read through EVSRM; otherwise a file name, through EVSYN.

DOC EVSYN
    A file name for a syntax-checked command: EVNAM, and back at once
    at syntax time; otherwise on into EVSY2.

DOC HEVSY
    The hook's form of EVSYN: the name from the hook's registers through
    HEVNAM rather than from the line, then EVSY2 as before.

DOC CLMOV
    Close MOVE's file end: nothing to do if that end was a stream
    (SSTR1 holds &FF), else IX to the channel record NSTR1 names and
    DELD takes it out.

DOC DELD
    Delete the channel record at IX: its displacement from CHANS in
    the ROM's numbering into SVTRS -- the record's window address less
    &4000 -- and CLRCHD does the rest.

DOC HOOK_HOPEN
    Hook 134, open a stream onto a file: the character under CHAD,
    OPSR for the stream, the name from the hook's registers, and the
    stream number worked out from the STREAMS entry address in HKHL --
    &5C16 is stream 0's entry, two bytes a stream.

DOC OPDST
    Point the stream at the channel: the stream's STREAMS entry, two
    bytes a stream from &5C16, gets the channel's displacement once
    the channel scan has placed it; carry from the scan is an error
    and returns as it is.

DOC OPDST1
    The channel is permanent -- bit 7 off the letter, "D" not "D"+&80
    -- and the displacement in DE goes into the STREAMS entry at HL.

DOC OPND45
    OPEN when the scan did not find the name: IN needs a file that
    exists, so that is "File not found"; for the others a channel
    record is made through CRMCH, and its mode bits are 2 for RND and
    1 for OUT.

DOC OPND8
    The channel's displacement from CHANS in the ROM's numbering, into
    HL: IX less HEADER, less CHANS, plus one.  NC.

DOC HOOK_HCLOS
    Hook 135, close a stream: the stream number from the STREAMS entry
    address in HKDE -- &5C16 is stream 0's, two bytes a stream -- into
    SSTR1, and CLSRM closes it.

DOC CLOSE
    CLOSE *stream, or CLOSE * for every stream: "*" is insisted on,
    then either the end of the line, which is all of them, or the
    stream number, which CLSRM closes.  CLOSE #n is the ROM's own
    command and reaches the DOS through hook 135, HOOK_HCLOS.

DOC CLRCHD
    Take a channel record out: an IN file gives back its count in
    SAMCNT here; an OUT or RND file does so inside SDCM, which CLRC2
    calls next unless this is CLEAR #; then RCLAIM closes the record
    up.

DOC DECSAM
    One off SAMCNT, the count of long-term files open, and never below
    zero.

DOC HOOK_SBYT
    Hook 148, save one byte to the open file: A into the buffer at the
    write point; when the write point has reached the link bytes a
    fresh sector is found through FNFS and planted in the link, the
    full sector goes out, and the byte goes into the next.

DOC LBYT
    Hook 159, load one byte from the open file into A: the byte at the
    read point, after following the link to the next sector -- the
    buffer flushed if it was written to, the linked sector read in --
    when the read point has reached the link bytes.

DOC FPTR
    The file pointer as a flat address in A:HL: CNT less one sectors
    of 510 plus RPT, through M510, which counts BC down before each
    add.

DOC INVST
    Error code 21, "Invalid stream number", through DERR.

DOC SNOP
    Error code 47, "Stream is not open", through DERR.

DOC ICNT
    One on the channel's sector count, CNTL and CNTH.

DOC GLEN
    The open file's length as a flat address in A:HL: LEN MOD 510 from
    the channel's length field into HL and its sector count into BC,
    then M510 to add the sectors up.

DOC M510
    A:HL := HL + (BC - 1) * 510: the loop at PTAD2 counts BC down
    before each add, so a count of one adds nothing, which is how a
    length recorded as "first sector plus remainder" comes out right.
    BC is kept for GLEN's caller.
