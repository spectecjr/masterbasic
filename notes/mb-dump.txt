# The run-length encoder behind DUMP, &61D2-&62A1.  Read by hand.
#
# The nibble stream WRITE_NEXT_NIBBLE fills is not pixels: it is pairs
# of four-bit values, a run length and then the byte that repeats.
# READ_NEXT_NIBBLE at &6367 takes them back out again.

DOC NEXT_SCREEN_BYTE
    Step to the byte below the current one on screen.

    The display file is laid out the way a Spectrum's is, so moving down
    a pixel row is INC H until the row crosses into the next third, and
    the INC L / DEC H / DEC H around it is that carry being fixed up.
    Reading a column downwards is the order a printer wants its bit
    image in, which is why the encoder above walks the screen this way
    rather than along each line.

DOC COUNT_RUN
    Count how many bytes below this one are the same, up to 139.

    B starts at &8B and counts down while NEXT_SCREEN_BYTE keeps
    returning the byte held in E, so &8C minus B is the length of the
    run.  The odd starting value is what makes the arithmetic below come
    out with the short cases first.

DOC ENCODE_RUN
    Write one run to the nibble stream.

    A run shorter than four is not worth encoding and goes elsewhere.
    From four to eleven it fits in a single nibble pair.  Longer than
    that and the length is split, the top half rotated into place and
    emitted first, so a long run costs three nibbles instead of two.

DOC EMIT_RUN_PAIR
    Write a run as two nibbles: the count in C, then the value in E.

MB &627E NEXT_SCREEN_BYTE
MB &61D2 COUNT_RUN
MB &61DE ENCODE_RUN
MB &61F8 EMIT_RUN_PAIR

# OPEN: what page is at &4000 in DUMP 5, the text dump.
#
# &6AF9-&6BE0 reads what look like the ROM's own dump variables straight
# -- &5A12, &5A13, &5A15, &5A1F, &5A2D, &5A39, &5A40 -- and the
# Technical Manual names that whole run: DMPLEN, DMPWID, DMPWM, DMPHM,
# GCM2, DMPTL, UWLHS and MODE, with DEVICE at &5A73 and PRRHS at &5A0E
# a few instructions away.  Reading them at those addresses needs the
# ROM's system page at &4000.
#
# It cannot have it.  The same stretch does CALL &500B at &6B4A and
# &6B5F and CALL &5015 at &6B9F, and those are this half's own routines
# next to HPRTOK; &500B is also called from &5221, which is ordinary
# code.  In the system page &500B holds character bitmap data --
# 00 08 14 00 1C 22 22 1C -- so it is not a call target there.
#
# So one of the two readings is wrong and I cannot yet say which.  A
# sys_low range was tried and reverted: it named UWLHS, MODE, SCRNBUF
# and M23PAPP correctly and turned two working calls into calls on
# character data, which is not a trade worth making.
#
# What the DE values are, which sharpens the question rather than
# answering it: &5A16 and &5A1F are GCM1 and GCM2, the graphic dump
# control strings, and the manual says of that family "first byte is the
# number of characters to send".  So &500B should be a routine that
# sends a counted control string to the printer, and both calls are
# handing it one.
#
# GTDT at &5000, which &500B sits inside, is a trampoline:
#
#     POP IY : LD BC,&0011 : ADD IY,BC : POP DE : ADD HL,DE
#     EX DE,HL : LD (HL),&FF : JP (IY)
#
# It takes its own return address into IY, steps it on by 17, and jumps
# there -- so the caller's next 17 bytes are data it skips.  &5005 is the
# entry for when IY is already set, and &5221 pushes &500B and &5005 as
# return addresses before letting something RET into them.
#
# The thing to check next is &500B itself.  &500A is DEFB &36 skipped,
# the LD (HL),&FF idiom, so &500B is the &FF of that instruction and
# reads as RST &38 followed by JP (IY) -- which is a strange thing to
# CALL, and may mean the entry point is misaligned rather than the
# paging misread.
