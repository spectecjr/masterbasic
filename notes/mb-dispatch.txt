# The dispatcher in the installed block.

# The seven blocks it branches to carried the dispatcher's own name with
# a number or a DONE on the end, which said where they sat and nothing
# else -- the auto-namer's answer when nothing better is known.  Five
# are stubs that pop the ROM's return address and fire one hook, so they
# take that hook's name the way CALLBACK_HCMDV already does -- and the
# HOOK_ prefix stays with the handlers in MasterBASIC's own page, which
# is what these call.  The other two are tests, and are named for the
# test.

# Named by address rather than by RENAME.  A RENAME has to say what a
# label is called now, and the synthetic numbering is not stable while
# this file is renaming things: naming &7C95 and &7CA0 below took _1 and
# _2 out of the run, the namer renumbered what was left, and the RENAMEs
# for _3 and _4 then matched nothing.  An address cannot shift.

MB &7CAA CALLBACK_CSIZE
MB &7CAE CALLBACK_SWAPCHARS
MB &7CB2 CALLBACK_COMADENT
MB &7CB5 CALLBACK_SKIPNAME
MB &7CBA CALLBACK_RCPTCH

MB &7D09 : the high byte of the word under the return address, against &40.  INC D below moves it to &41, and SYS_DH_STATE is given the &40 to remember that it did

MB &7D11 : and against &42, which DEC D brings down to &41 as well -- but only when SYS_DH_STATE says the &40 case came first, so the two are a pair and not two tests

MB &7D18 : the same &40, read back out of SYS_DH_STATE.  SUB does both halves of the job: it tests for the marker and leaves the zero that clears it

MB &7D25 : DEVICE 2 is the printer, which the ROM's own variable list gives as "0=US, 1=LS, 2=PRINTER"

MB &7D4E : &16 is AT.  ref/samrom/tprint.asm's control-code table has "22 AT" against it

MB &7D52 : &17 is TAB, 23 in the same table, and the pair is what this stub exists to catch

MB &7D64 : &4A12 is this block's own &7D69 once it is running at &484D, and TBL_7D58_1 below writes it through CURCHL -- so AT points the channel at that handler.  The overlapping stream entered at &7D69 loads &4A1F instead, which is the next one along

MB &7D00 PATOUT_CHAR_OUT
    MasterBASIC's character output, which runs at &49A9 -- the address
    the listing already had an equate for, SYS_PATOUT_CHAR_OUT, because
    PATOUT is one of the ROM vectors the first stub redirects.  It reads
    DMPFG, then DEVICE, then SYS_CHAR_WIDTH and SYS_CHAR_HEIGHT, and
    hands a character to PRINT_SIZED_CHAR or PRINT_MAGNIFIED_CHAR
    accordingly.

    IT IS NOT A ROUTINE HEAD AND THE LABEL HERE ONCE SAID IT WAS.  The
    only reference to &7D00 in the image is LD DE,&7D00 at &7B78, which
    is a destination and not a call, so the label read
    INSTALL_ROM_PATCHES_3 and the blocks after it were parented to
    whatever underived label came before -- CALLBACK_HCMDV once, and
    CALLBACK_RCPTCH after the stubs were renamed.  Both were wrong.

    THE ADDRESS HAS TWO LIVES AND INSTALL_ROM_PATCHES GIVES IT BOTH,
    sixteen instructions apart.  &7B51 copies &7BA4 to &884D, &029F
    bytes -- so &7BA4-&7E42 goes to system page &484D-&4AEB, and &7D00
    is inside it, landing at &49A9.  Then &7B75 copies &8009, the DOS
    page's own &4009 past its nine header bytes, back to &7D00 for &F0
    bytes.  The code is installed first and the space it occupied is
    then refilled with the boot sector, which is what SAVE BOOT writes
    out later.

    So notes/mb-saveboot.txt's "&7D00-&7DEF the DOS's boot sector" and
    this listing's code at the same address are both right, of the same
    bytes at different moments: that map is headed "WHAT MASTERBASIC'S
    PAGE ACTUALLY HOLDS AFTER A BOOT" and was read from a memory dump.
    Neither is an offset into a file on disc.


# One line on each stub, saying what the hook it raises goes on to do.
# Every one of them pops the ROM's return address first, so the hook
# returns to the ROM's caller and not into the stub.

MB &7C92 : hook 177, HOOK_TOKENARG at &52FD: it takes the character after the function prefix and dispatches on it, which is how the argument of one of MasterBASIC's own functions gets read.  Anything it does not know reports "Not understood"

MB &7CA7 : hook 173, HCMDV at &4E96 -- the same dispatcher the ROM's CMDV points at, reached here for the commands that need no test beyond their token

MB &7CAB : hook 155, HOOK_CSIZE at &6534: the manual's "Improved CSIZE", which reads the arguments itself and then enters the ROM's own WIDTH past the range checks it would otherwise fail

MB &7CAF : hook 156, HOOK_SWAPCHARS at &7159: BLOCKS 0, 1 or 2, which picks the character set to swap in -- 1 being the one that changes nothing

MB &7CB3 : hook 183, HOOK_COMADENT at &6F3E: finds an entry through COMAD.  There is no RET after it -- EDIT raises this hook and then falls into the one below

MB &7CB5 : hook 178, DELETE for strings and string arrays.  The LD A below leaves &CD in A, which is DELETE's own token

MB &7CBB : hook 174, HOOK_RCPTCH at &51DD -- the slot MasterDOS calls RCPTCH and MasterBASIC replaces.  RUN and CLEAR both come here, and what follows waits for the raster before switching screens

MB &7C95 INTERCEPT_SOUND_CLEAR
    SOUND is worth intercepting only when CLEAR follows it, which is the
    buffer command the manual documents; a plain SOUND is the ROM's.

    IT DOES NOT RETURN WHEN THE ANSWER IS NO.  The JR Z leaves for
    CALLBACK_HCMDV and everything else falls into INTERCEPT_IF_RECORDING
    below, so a plain SOUND still gets the recording test.  That is not
    an accident of layout: the manual has RECORD SOUND capturing "the
    SOUNDs and the PAUSEs that determine their length", so both commands
    have to add codes to the string being recorded, and both reach the
    hook by this one fall-through.

MB &7CA0 INTERCEPT_IF_RECORDING
    Reached by PAUSE directly and by a plain SOUND falling through from
    above.  RET Z when SYS_RECORD_STATE is zero: with no RECORD running
    neither command needs MasterBASIC at all, and the ROM's own routine
    is left to it.

    Naming this after PAUSE alone would be wrong -- half its callers are
    SOUNDs.

DOC DISPATCH_ON_COMMAND_TOKEN
    Switch on a command token in H, for the commands MasterBASIC has
    something to add to.

    Running at &48FA in the system page, not here.  Anything below &94 is
    let through untouched, and the rest are ordinary ROM command tokens:

        &94-&97     &A9 BLOCKS   &B0 RUN         &CD DELETE
        &A8 CSIZE   &AA MODE     &B3 CLEAR       &D1 KEYIN
                    &AC PUT      &C2 PAUSE       &E1 POKE
                    &AE SOUND    &C9 DEF KEYCODE

    &94-&97 are SAVE, LOAD, MERGE and VERIFY, taken as a range by the
    CP &98 : JR C at &7C8A rather than one at a time -- the ROM's own
    table gives all four the same routine, SLMVC.  &98 OPEN is NOT among
    them, which the JR C makes plain: it is taken only for A below &98,
    so &98 itself falls through to the CP &FF at &7C8E and returns
    untouched.

    with &FD and &FF, which the ROM's table does not name, handled last.

    PUT goes to TOKEN_TO_FN_INDEX, the ten bytes installed at &45A2,
    which subtracts &AB and stores the result at &4AF0 in the system
    page -- so PUT
    arrives there as 1.

    An earlier note here doubted that H held a token at all, on the
    grounds that &C2, &C9, &CD, &D1, &E1 and &FF were past the end of the
    range.  That was wrong: &B9 is where the hook codes stop, not the
    tokens, and every value in the list above is a command.


# ALTER DISPLAY: what CALLBACK_RCPTCH falls into, and the one piece of
# MasterBASIC that has to finish inside a scanline.
#
# THE BLOCK FROM &7CBD ON IS NOT WHERE IT RUNS.  It is byte-identical to
# &4966 in listings/*/postinstall-syspage.asm, because INSTALL_ROM_PATCHES
# copies &7BA4-&7E43 to &484D and so lands &7CBA at &4963.  &4966 is the
# address CMD_ALTER writes into ANYIV, so this is the maskable interrupt
# handler and the copy in the system page is the one that runs.  ALTER
# DISPLAY OFF writes &0049 into ANYIV instead, which is the ROM's own
# ANYI, and that is what proves what these bytes are.
#
# CMD_ALTER at &54EA sets the whole thing up from ALTER DISPLAY n TO m
# LINE y: ANYIV, then ALTDISP_TOP and ALTDISP_BOTTOM as one word, then
# LINICOLS, then &5604.  The last two put y in the scan-line field of the
# first entry of the ROM's line-interrupt palette list and terminate the
# list after that one four-byte entry -- the two share the table, which
# is why the manual says PALETTE will act unpredictably while ALTER
# DISPLAY is running.

MB &51DD HOOK_RCPTCH
    Hook 174, the slot MasterDOS calls RCPTCH.  MasterDOS's own name for
    it says which commands it serves and the table settles it: &51F1
    takes COMAD plus &40, which is entry 32 and so token &B0, RUN; five
    bytes further on is COMAD+&46, entry 35, token &B3, CLEAR.  Both
    routines' addresses are read out of the ROM's own table with ROM 1
    paged in, so neither has to be known when this is assembled.

    IT COPIES WHICHEVER OF THE TWO LIES LOWER.  The SBC HL,BC at &520D
    compares them and only the branch is different afterwards: RUN below
    CLEAR copies &3F bytes from RUN, and otherwise &41 from CLEAR.  Two
    return addresses are pushed either way, and they differ too -- &5000
    under &500B on the first path, &5005 under &5000 on the second.  The
    span has to reach both routines, so which one it starts from decides
    how far it runs.

    What comes back is an address, and the CP at &5266 picks it: CLEAR
    keeps what was built and RUN takes DE instead.

MB &51F1 : COMAD plus &40 -- entry 32 of the ROM's command table, which is token &B0, RUN

MB &51FF : five on from RUN's high byte to CLEAR's low.  &B3 is three entries past &B0 and each entry is two bytes, so the step is six less the one INC HL has already made

MB &521C : &41 bytes, the span from CLEAR when CLEAR is the lower of the two

MB &5221 : &500B, pushed under the &5000 below it as the second return address

MB &5225 : and &5000, which is where the copy lands and so where control goes first

MB &5228 : &3F bytes, the span from RUN when RUN is the lower

MB &5230 : two bytes more, unless the byte below is taken as well and the DEC C makes it one

MB &523A : three added to the byte just read, which is the operand being fixed up rather than copied

MB &5245 : the four bytes at V5272, a CALL and a JP with the JP's operand still to come

MB &524B : three on, to the operand of that JP

MB &5259 : &24 into the code buffer at &4D38, patching what BUILD_COMPILER laid down two instructions earlier

MB &525B : &4D38 seen through the window

MB &5266 value T_CLEAR
MB &5266 : the token that came in, so CLEAR leaves with what was built and RUN with DE

MB &54E1 : &0049 is ANYI, the ROM's own frame-interrupt entry, so ALTER DISPLAY OFF hands the interrupt straight back to it

MB &54E4 : zero into ALTDISP_TOP and ALTDISP_BOTTOM, which go out as one word

MB &54E7 : &FF into LINICOLS, no split line

MB &54FA : and &FF into &5604, which ends the palette list after its first entry

    At the split line, show the bottom screen.  &5C9F + screen indexes
    SCLIST, whose entry is a ready-made VMPR value: the mode in bits 6
    and 5, the page in bits 4 to 0.

MB &7CCB : the split line, which CMD_ALTER wrote into the first entry of the palette list

MB &7CCF : zero, which is what the INC A below counts on

MB &7CD0 WAIT_NEXT_SCANLINE
    Holds until the raster leaves the split line, so that the write to
    VMPR below happens in the next line's border and cannot be seen.  The
    ROM does the same thing at the same port in LNWAITLP, and comments it
    "WAIT FOR NEXT SCAN'S BORDER" -- see ref/samrom/scrsel1.asm.

    THE LOOP WAITS FOR THE LINE TO END, NOT FOR IT TO ARRIVE.  The SUB H
    is followed by a jump taken on zero, so this goes round while the
    raster is still on line H and leaves as soon as it is not.

    A is zero at the label whichever way it is reached: XOR A above on
    the way in, and SUB H having left zero on the way round.  So the
    INC A counts nothing.  It is there to put 1 on the top half of the
    address bus, because the port wanted is &01F8 and not &00F8, and the
    loop depends on A being reset to zero every time.

MB &7CD1 expr LPEN

MB &7CD1 : uses HPEN; A is 1 when read, so the port is &01F8 -- the raster line, and not the light pen the byte alone would give

MB &7CD4 : goes round while the raster is still on line H

MB &7CD9 : B is the LMPR the ROM read at &003D before it took the vector here

MB &7CDA value ANYI_EXIT

MB &7CDA : a line interrupt is finished here, so INTS never runs -- no keyboard scan and no FRAMES tick, neither of which would fit inside a scanline

MB &7CDD step
    From here down is the frame interrupt, not the line interrupt: this
    is what &7B51 lands at &4986, which is the address INSTALL_ROM_VECTORS
    writes into FRAMIV.  It puts the top screen back at the start of
    every frame, so a split that the line interrupt made is undone and
    remade fifty times a second.

MB &7CE3 : zero when there is no split

MB &7CF1 FRAME_INT_CALL_INTO_MB
    NAMED HERE BECAUSE OF WHAT RENAMING THE LOOP ABOVE DID TO IT.  It had
    no name of its own, so it took the nearest underived label above and
    a number on the end, and renaming that label carried this block --
    which waits for nothing and is not on the line interrupt's path at
    all -- along with it, under a name about the raster.  The warning at
    &7D00 below is about the same thing, three lines further on.

    Both tests above arrive here, and so does the screen switch falling
    through: it is the frame interrupt's tail whatever was done with the
    display.  HMPR is saved and put back around the call, and D carries
    the old value in as well.

MB &7CF5 step
    MasterBASIC's own page number, which is not known until it is
    installed.

MB &7CF9 : with MasterBASIC at &8000 the routine called runs at &99A3, which is why its header says the paging is the opposite way round there
