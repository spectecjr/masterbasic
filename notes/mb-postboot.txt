# What file/MBPOST.bin actually is, and what may be concluded from it.

# IT IS NOT A MEMORY DUMP.  It is the output of SAVE BOOT, made by
# booting dsks/MasterDOS2_3_MasterBasic1_7.mgt under SimCoupe and then
# saving to a freshly formatted disk.  The name is a leftover from when
# this file was believed to be a dump of the two halves after boot, and
# several conclusions were drawn on that basis which had to be withdrawn.
#
# The distinction matters because SAVE BOOT does not copy two pages.  It
# assembles eight blocks from four different places -- see
# notes/mb-saveboot.txt -- so only some of the file is the memory whose
# address it occupies:
#
#   block   file offset      source                    live?
#     1         0-  255      MB &7CF7                  yes, but MB's
#     2       256-15711      the DOS page &4100        yes
#     3     15712-16157      MB &7DF0                  yes, but MB's
#     4     16158-16319      system page &4C14         no
#     5     16320-31551      the MB page &4000         yes
#     6     31552-31587      system page &4BA0         no
#     7     31588-32258      system page &484D         no
#     8     32259-32639      system page &5896         no
#
# So a byte at "DOS &7F30" in this file is not the DOS page's &7F30 at
# all; it is the system page's &4C26.  Only blocks 2 and 5 can be read
# as the pages they appear to be.

# WHAT IT CONFIRMS, and this is the valuable part.
#
# The eight blocks above were derived by reading SAVE_BOOT at &6404 --
# the addresses, the lengths and which page each comes from -- before
# any file was known to exist that had been through it.  This is such a
# file, and every block whose source can be checked against the system
# page dumps matches byte for byte:
#
#     block 4   DOS &7F1E, &00A2 bytes  vs syspage &4C14   162 of 162
#     block 6   MB  &7B80, &0024 bytes  vs syspage &4BA0    36 of 36
#     block 7   MB  &7BA4, &029F bytes  vs syspage &484D   671 of 671
#     block 8   MB  &7E43, &017D bytes  vs syspage &5896   381 of 381
#
# That is the whole layout verified from the outside.

# WHAT IT CANNOT SHOW, which matters as much as what it can.
#
# Only blocks 2 and 5 are the live pages they appear to be, so of the
# two pages a booted machine actually holds, this file covers:
#
#     the DOS page        &4100-&7D5F     blind: &4000-&40FF, &7D60-&7FBF
#     MasterBASIC's page  &4000-&7B7F     blind: &7B80-&7FBF
#
# Both blind spots are there for the same reason: SAVE BOOT fills those
# slots from somewhere else precisely because the running machine no
# longer holds what the file needs there.  &4000-&40FF is the boot
# sector and &7D60-&7FBF the DOS's tail, both boot-time-only code that
# has been overwritten by the time anything could save it.
#
# So a search of "the DOS page after boot" using this file is really a
# search of &4100-&7D5F, and a routine that lives in the tail would not
# appear.  Anything concluded from not finding something here has to say
# which range it looked in.  A straight dump of the two pages from a
# booted machine is the only thing that covers them.

# WHAT DIFFERS FROM THE SHIPPED IMAGE, by block.
#
#     1    15 of   256      3    0 of   446      5   50 of 15232
#     2   478 of 15456      4    6 of   162      6    0 of    36
#                                                7   20 of   671
#                                                8  325 of   381
#
# Blocks 2 and 5 are the two that are really live memory, and they
# behave as a booted machine should.
#
# Block 5, the MasterBASIC page: almost every difference is a two-byte
# run at an address RESOLVE_ROM_ENTRIES writes to -- &45F6, &56F6,
# &59C1, &5CF2, &6517, &6594, &735E, &73B4, &73BA, &73BF, &73F8, &7429,
# &7468, &757F, &7596 -- plus the single bytes that carry this half's
# own page number.
#
# Block 2, the DOS page: the DOS's working variables and UIFA around
# &4100-&4AFF, and then DCHAN at &7C00 with FSA and DRAM after it, which
# the annotated source calls the disk channel record, "the 256-byte
# image of a directory entry" and "the sector buffer proper".  A machine
# that has booted has read its boot sector and looked at a directory, so
# all of that holds live data.  &78E2 is in this block too: it is
# INDJP's own CALLMB operand, rewritten on every cross-page dispatch,
# and it holds &4E96 -- HCMDV -- because that is the last one a machine
# at a prompt performed.
#
# Blocks 7 and 8 differ for a reason that is not about memory at all:
# their source is the system page, so what they hold is the installed
# stub with its boot patches applied, and the DEF KEY gap, the keyboard
# table and the DUMP settings.  Of course they do not match a file that
# has never been booted.

# THE ROM SEARCHES, which stand however the file was made.
#
# Fifteen of the signature searches are followed by a plain LD (nn),HL,
# so their answers can be read straight out of block 5.  All fifteen are
# exactly what running the search against the ROM this project
# assembles predicts -- CCRESTOP, ENDOUTP, EPSUB, PRMAIN, POKE2, DOCOMP,
# COMDF, COMLEN, LKCALL, MATCHER, LKFC and the rest.  The machine that
# made this file is running ROM 3.0.

# WITHDRAWN.
#
# For several days this file was read as a dump, and that produced a
# "381-byte copy with no copier": MasterBASIC's &7E43-&7FBF appeared to
# hold the system page's &5896-&5A12 with nothing writing it.  Two write
# breakpoints on a real machine, at &7E6B and then at &7E8E, caught
# nothing but the ROM's MNINIT clearing the page at reset.  They were
# right.  Block 8 never was in MasterBASIC's page; SAVE BOOT reads it
# out of the system page and writes it into the file.
#
# Also withdrawn: "&7800-&7B05 is not overwritten at boot" and "the last
# LDIR in the installer had not run", both of which compared block 5
# against parts of the file that are not block 5's source.  They may
# well be true; they are not shown by this file.

MB &7DF0 : the installer saves the ROM's transfer buffer here, and SAVE BOOT reads it back out as its third block -- which also carries the alternate character set at &7E64, see notes/mb-saveboot.txt
MB &7D00 : and the DOS's boot sector here, which is the first block
