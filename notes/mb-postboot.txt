# What a booted machine actually holds.

# file/MBPOST.bin is the two halves dumped after boot, in the same shape
# as the original image, and file/SYSPAGE.bin is &4000-&4BFF of the ROM's
# system page.  894 bytes of the two halves differ from the file: 499 in
# the DOS page, 395 in MasterBASIC's.  Most of what follows could not
# have been settled by reading.
#
# All 499 of the DOS page's are accounted for below, and all but two of
# them are ordinary live state rather than anything installed.

# THE DOS PAGE'S 499 BYTES, ALL OF THEM
#
# They fall in 42 runs and every run has an owner:
#
#   150 bytes, 28 runs   &4000-&4AFF, the DOS's working variables
#   341 bytes, 10 runs   &7C00-&7F12, DCHAN, FSA and DRAM
#     6 bytes,  3 runs   &7F13-&7F8F, PTH1 and PTH2
#     2 bytes,  1 run    &78E2, INDJP's own CALLMB parameter
#
# The big one is not a mystery at all once the annotated source's own
# layout is put beside it.  DCHAN is the disk channel record at &7C00 --
# SVBC, SVDE, RFDH, SVHL, SVIX, REG1, DRIVE, FLAG3, RPT, BUF, NSR -- and
# then FSA at DCHAN+19, which the source calls "the 256-byte image of a
# directory entry", and DRAM at FSA+256, "the sector buffer proper".
# A machine that has booted has read its boot sector and looked at a
# directory, so all three hold live data.  PTH1 and PTH2 after them are
# the current path for each drive, which the source puts at DRAM+512.
#
# The 150 are the same kind of thing one page down: the listing already
# carries MasterDOS's own comment on each byte, and they read as what a
# DOS that has done something would have -- &412F "HMPR value that maps
# the page used as a buffer", &4150 "whole 16K pages remaining in the
# transfer", &4151 "page of the transfer address", and the 44 bytes from
# there running into UIFA at &417D, "the header the caller asked for".
#
# The odd two are not a boot-time patch at all.  &78E2 is the DEFW after
# the CALL CALLMB at &78DF, and three instructions before it is

#     L78D9:  RES 7,H
#             LD (L78DF+3),HL      -- &78E2
#             EXX
#     L78DF:  CALL CALLMB
#             DEFW &0000           -- &78E2

# which is INDJP, the indirect jump this file's neighbours already
# describe: "an entry with bit 15 set does not live in this page.  The
# bit is cleared, leaving the address as the other page numbers it, and
# the call goes through CALLMB instead of a plain JP".  So those two
# bytes are rewritten on every cross-page dispatch, and the dump simply
# caught the last one.

# That it caught &4E96 is the nice part.  MB &4E96 is HCMDV, which CMDV
# reaches for every command the machine executes -- so on a machine
# sitting at a prompt it is the likeliest value there could be.

# MASTERBASIC'S 395, AND A FOURTH COPY THAT GOES THE WRONG WAY
#
# 54 runs.  Two are big and the rest are two bytes each:
#
#   323 bytes, 17 runs   &7E6B-&7FBF
#    72 bytes, 37 runs   the patch sites, listed under CONFIRMED below
#
# The large one was a surprise.  After boot, MasterBASIC's &7E43-&7FBF
# is an exact copy of the ROM's system page at &5896-&5A12 -- all 381
# bytes, checked against file/SYS2.bin.  The file holds a fragment of
# somebody's BASIC program there; the running machine holds the DEF KEY
# gap, the whole keyboard table and the DUMP settings.
#
# So this is a fourth copy that runs the wrong way, alongside INSTBUF to
# &7DF0 and the boot sector to &7D00.  What makes it is not found: no
# LDIR anywhere in either half carries a length of &017D, and the only
# instruction in the image that mentions that number at all is SAVE_BOOT
# handing it to SVBLK.  The boot sector has been read for it and does
# not do it either.
#
# It matters for notes/mb-saveboot.txt, which called SAVE_BOOT's last
# block a filler whose source was incidental -- &5896 "because that is
# where the previous block's neighbour begins".  That was wrong.  The
# same 381 bytes sit in both places on a running machine, so the block
# is a saved copy like the two before it and SAVE_BOOT could read it
# from either.

# CONFIRMED
#
# The ROM searches.  Fifteen of the signature searches are followed by a
# plain LD (nn),HL, so their answers can be read straight out of the
# dump.  All fifteen are exactly what running the search against the ROM
# this project assembles predicts -- CCRESTOP, ENDOUTP, EPSUB, PRMAIN,
# POKE2, DOCOMP, COMDF, COMLEN, LKCALL, MATCHER, LKFC and the rest.  The
# machine that made this dump is running ROM 3.0.
#
# The patch sites.  Almost every difference in MasterBASIC's page is a
# two-byte run at an address RESOLVE_ROM_ENTRIES writes to: &45F6, &56F6,
# &59C1, &5CF2, &6517, &6594, &735E, &73B4, &73BA, &73BF, &73F8, &7429,
# &7468, &757F, &7596.
#
# The stubs are patched before they are copied.  Stub one's source at
# &7460 differs from the file in 6 bytes and stub two's at &7BA4 in 20 --
# the same counts, at the same offsets, as the copies at &46CC and &484D
# in the system page.
#
# INSTBUF.  &7DF0-&7FAD differs in 311 of its 446 bytes, which is the
# copy out of the ROM's transfer buffer that the installer performs.

# CORRECTED
#
# &7800-&7B05 is not overwritten at boot.  6 of its 774 bytes differ, so
# the DOS buffers do not land there during startup.  DOS &5ADD sets up
# HL, DE and BC and returns; something else does the copying, and only
# when that path runs.  An earlier note here said the region "becomes DOS
# buffers", which overstated what had been shown.
#
# The last LDIR in the installer had not run.  &7D00-&7DEF differs in
# only 14 of 240 bytes and matches neither the DOS page's &4009 nor the
# system page's, so the 240-byte copy at &7B75 has not happened by the
# time the machine is sitting at a prompt.

DOS &5ADD : a buffer address, not a routine -- the caller does the copy
MB &7DF0 : overwritten at boot with the ROM's transfer buffer
MB &7D00 : still holds the file's bytes on a freshly booted machine
