# What else is on the disk images, and what it settles.

# dsks/ holds three images.  Files come out of them by following the
# sector chain -- each 512-byte sector is 510 bytes of data and then the
# track and sector of the next -- and the directory is two 256-byte
# entries per sector across track 0.

# dsks/MasterBasic1.7.dsk
#
#   samdos2   type 19, 10200 bytes   SAMDOS 2
#   MBMC      type 19, 16311 bytes   saved from &8009, page 97
#   MBASC     type 19, 16320 bytes   saved from &BFC0, page 97
#   autoMBM   type 16                a BASIC loader
#   ...and the demonstration programs the manual refers to: alter, edit,
#   sort, join, inarray, sval, the sound and PUT examples
#
# MBASC is this project's MasterBASIC half, byte for byte -- all 16320
# of them, once its own nine-byte header is skipped.  So the same binary
# ships paired with SAMDOS and with MasterDOS, and there is no second
# build of MasterBASIC 1.7 to compare against.
#
# MBMC occupies the DOS's slot and is not a DOS.  Its header records
# &8009 and &3FB7 where MBASC's records &BFC0 and &3FC0, and those two
# runs are contiguous: &8009 to &BFBF and then &BFC0 to &FFBF, 32K in
# all.  So the pair were saved from the same arrangement the combined
# file loads in one piece, split into two files.  The slot is right.
#
# The page byte is the saved address divided by 16384.  The ROM's
# SAVE "name" CODE path calls UNSTLEN -- "split the calculator stack top
# into a page count and an offset" -- and stores A, E and D at HDR+31,
# with SET 7,D forcing the high byte into the &8000 window.
#
# So MBMC's 97/&8009 is 1589257 and MBASC's 97/&BFC0 is 1605568, and
# MBMC's 16311 bytes end at exactly 1605568.  The two are contiguous,
# which is the check on the reading rather than an assumption in it.
# The combined file is 99/&8000 = 1622016 and samdos2 125/&8009 =
# 2048009.  All are past 512K, so these were saved from external memory
# on the machine that built them; 97, 99 and 125 are Module 1 in the
# 8-bit external paging.
#
# Nothing here reads it.  PAGE1 is written once at &63A7 and the only
# access to &4151 in either half is that one LD (PAGE1),A.
#
# The contents are not code.  It begins 0C DE FF FF DD 1D A5 D1 where a
# DOS begins DI : LD HL,&0000, it holds no readable text at all where
# samdos2 has its error messages, and all 256 byte values appear in it.
# The extractor is not at fault: MBASC comes out of the same image byte
# for byte, and `alter` from the same directory comes out as readable
# BASIC.
#
# It is not compressed either, or not in a way that would show: a
# compressed file would occupy fewer sectors than its length implies,
# and MBMC's 16311 bytes take the 32 sectors 16311 bytes need.
#
# WHAT AUTOMBM SAYS IT IS, which settles the role if not the bytes.
#
# autoMBM is the BASIC program that builds the combined file, and it is
# on the same disk.  Detokenised with tools/mgt.py and a crude renderer,
# its first lines are:
#
#     70  PRINT "LOADing MBMC"
#     80  LOAD "MBMC"  CODE &8009
#     90  PRINT "LOADing MBASC"
#    100  LOAD "MBASC" CODE &BFC0
#    ...
#    360  POKE 65536, MEM$(&8009 TO &FFBF)
#    390  SAVE a$ CODE 65536, 32631
#
# &8009 plus MBMC's 16311 bytes is &BFC0 exactly, where MBASC begins,
# and &8009 to &FFBF is 32631 bytes -- which is the combined file's
# length as its own header records it, 1 x 16384 + 16247.  So MBMC
# occupies the DOS half's slot and MBASC the MasterBASIC half's, and the
# saved file is the two of them end to end.
#
# The &09 is the nine-byte header.  It is part of the file, so it
# occupies the DOS page's &4000-&4008 when the file is loaded, and the
# DOS's own code starts at &4009.  MBMC loads at &8009 because it is the
# DOS half WITHOUT those nine bytes; autoMBM writes them itself.
#
# Two more of the manual's claims fall out of the same program:
#
#    250  IF dos=1 THEN ... POKE ndvs+7,21      SAMDOS
#    260  IF dos=2 THEN ... POKE ndvs+7,50      MasterDOS
#
# with ndvs = &8220, which is DOS &4220, the DVAR block -- so ndvs+7 is
# DVAR 7, and 21 and 50 are exactly the numbers the manual's
# introduction gives.  And line 350 builds the output filename from
# PEEK &BFC7, which is MB &4007, XVAR 7, "VERSION.  number of
# MasterBASIC, times 10" -- which is where the 17 in MD+MBAS17 comes
# from.
#
# WHY MBMC'S BYTES ARE NOT THE DOS HALF: IT IS PACKED, AND IT UNPACKS
# ITSELF.  autoMBM line 210 reads
#
#     LET dos = USR &BC00
#
# and &BC00 is inside MBMC, which loads at &8009.  An earlier reading of
# this file said autoMBM "never invokes machine code", which was wrong:
# the search was for the CALL token, and USR is a function, &FF &5F.
#
# The bytes at &BC00 are code, and unmistakably so:
#
#     LD BC,&0602 / LD HL,&7213     parameters
#     DI / LD (&BD3A),SP            save the stack
#     LD A,&03 / OUT (&FA),A        LMPR: pages 3 and 4 at &0000 and &4000
#     LD SP,&8000                   borrow the stack for the work
#     CALL &BD3D / CALL &BD2C       twice, with a second pair of
#     LD BC,&67D9 / LD HL,&4400     parameters and A=1
#     CALL &BD2C
#     LD SP,(&BD3A)                 put the stack back
#     LD BC,&1FFA / OUT (C),B       LMPR := SYSPAGE_IN_B
#     LD A,&C9 / LD (&BC00),A       plant RET over its own entry
#
# The last of those is the giveaway that it is meant to run once: after
# it has, USR &BC00 returns immediately.  And the value it returns is
# what autoMBM tests on the next line -- 1 for SAMDOS, 2 for MasterDOS --
# so it inspects the DOS loaded at &14000 as well as doing its own work.
#
# That accounts for everything the file looked wrong about.  Entropy of
# 7.19 bits a byte, 0.9% zeroes and not one readable string are what
# packed data looks like; 5.9% agreement with the DOS half is what
# packed data agrees with; and nothing had to decompress it in autoMBM
# because the decompressor travels inside it.
#
# The packing format is not read here, and nothing needs it: the DOS
# half of file/MasterBasicMasterDos.bin is the unpacked result, and that
# is the thing this project disassembles.
#
# Nothing here depends on knowing.
#
# THE README ON THAT DISK IS NOT ABOUT MASTERBASIC.  It is Games
# Master's -- "All additions to this version of Games Master have been
# documented in the Third Edition of the manual" -- with a page of other
# Betasoft products after it, including "Secrets of the SAM ROM
# revealed!  The complete ROM 3 sourcelisting", which is what ref/samrom
# is.
#
# It matters because the README announces "New Function - KEY(key code)
# returns 1 if the specified key is pressed, or zero if not... Unlike
# INKEY, KEY can be used even if many keys are pressed at once."  That
# is a Games Master function, not a MasterBASIC one.  MasterBASIC's own
# name table at &50D8 holds twenty-eight keywords and KEY is not among
# them:
#
#     EXIT PROC EXIT DO EXIT FOR LOCN RESERVED EQU TICS SHIFT$ SVAL$
#     USING$ TIME$ DATE$ INP$ DIR$ FSTAT DSTAT FPAGES SCRAD INARRAY
#     XVAR NVAL BACKUP TIME DATE ALTER SORT JOIN EDIT
#
# What that pair settles: nothing in samdos2 or MBMC calls MasterBASIC's
# SIZE_EXTERNAL_MEMORY either.  See notes/mb-extmem.txt.

# dsks/liveboottest.mgt
#
#   MBPOST, SYSPAGE and SYS2 -- the three files already in file/, saved
#   as CODE files.  Nothing new.
#
#   MBPOST is NOT a memory dump.  It is a SAVE BOOT output, made by
#   booting the combined image and saving to this freshly formatted
#   disk; SYSPAGE and SYS2 are genuine dumps of the system page.  The
#   distinction is set out in notes/mb-postboot.txt and it matters: only
#   two of SAVE BOOT's eight blocks hold the memory whose address they
#   appear to occupy.
#
#   "file/LICENSE and COPYRIGHT.md" said so from the start -- "MBPOST.bin
#   is a post-installation SAVE BOOT MasterBASIC file" -- and this
#   project spent days concluding it the hard way instead.  Read the
#   provenance notes beside a binary before reasoning about it.
