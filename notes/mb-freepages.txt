# Memory in 1K blocks: how MasterBASIC allocates and gives back.

MB &5F16 ALLOC_1K_BLOCK
MB &5F7B FREE_BLOCK_CHAIN
MB &5FA7 FREE_PAGE_IF_EMPTY

DOC ALLOC_1K_BLOCK
    Find a free 1K block, in a page already ours or a fresh one.

    HMPR is zeroed first, so the &91xx it then reads is the system
    page's &51xx: ALLOCT, which the ROM's variable list describes as
    "MUST START AT PAGE EDGE.  32 BYTES - 1 PER PAGE".  L starts one
    below the current page and walks down.  Zero means the page is free
    and gets claimed; &20 means it is already MasterBASIC's and may have
    room; running off the end reports error 1, out of memory.

    A newly claimed page has its top sixteen bytes zeroed.  Those
    sixteen are one marker per 1K block: the page is divided into
    sixteen of them, and the marker at &BFF0+n says whether block n is
    in use.  &FF claims one.

    The block itself is at ((n * 4) + &83) << 8, which steps &400 --
    1K -- from &8300 to &BF00, and its last two bytes hold a link.  The
    top block is the exception, because &BFF0-&BFFF is the marker array
    itself: its link goes at &BFEE instead of &BFFE, which is the
    CP &BF : JR Z that keeps L at &EE.

DOC FREE_BLOCK_CHAIN
    Walk a chain of 1K blocks, releasing each, and give back any page
    left with none in use.

    Each step pages the next page in, clears that block's marker, asks
    FREE_PAGE_IF_EMPTY whether the page still holds anything, then reads
    the link at the end of the block: the first byte is the next block's
    marker index, the second the next page.  A zero index ends it.  The
    same &BFEE exception applies, tested here as INC A : JR NZ.

DOC FREE_PAGE_IF_EMPTY
    OR the sixteen block markers together, and if all are clear give the
    whole page back to ALLOCT.

    The write goes through WRA, so no paging is needed here: WRA zeroes
    HMPR, windows HL up by &4000 and puts it back.

# The manual says the same thing twice, in as many words.
#
#   "Space is allocated in 1K (1024-byte) units -- the value you supply
#    will be rounded up if need be."            (RECORD SOUND)
#
#   "Space is allocated in 1K units.  The number you supply is rounded
#    up, so LPRINT CLEAR 2048 and LPRINT CLEAR 1025 both reserve 2048
#    bytes (2K)."                               (LPRINT CLEAR)
#
# and it describes this pair's job from the outside: "LPRINT CLEAR 0 has
# the special function of turning off interrupt-driven printing and
# freeing the buffer space for other uses".  FREE_BLOCK_CHAIN is reached
# from &5596, straight after the call that loads the print buffer's
# pointers into V4088 and V4089, which is what that sentence describes.
#
# The buffer itself is the chain: "this buffer space can be anything up
# to 256K, depending on the free memory available", which is sixteen
# pages of sixteen blocks.
#
# What this is not.
#
# Only HMPR is touched, never XMPRL, so these are ordinary internal
# pages; the external memory ports appear in exactly two places in the
# image, SIZE_EXTERNAL_MEMORY at &77DB and the DOS's "SELECT MEGA RAM"
# at &75B2, and neither is here.  And the sixteen bytes are at the top
# of a page, not the start: &BFF0-&BFFF is offset &3FF0 into whichever
# page HMPR has in the window.
#
# ALLOCT and the markers are two levels of the same scheme rather than
# alternatives -- ALLOCT says which pages are MasterBASIC's, the markers
# say which kilobyte of a page is in use, and a page goes back to ALLOCT
# only when all sixteen of its markers are clear.
#
# The decisive detail, if this is ever in doubt again, is that the block
# address is computed from the marker index and lands inside the same
# page: marker n at &BFF0+n names the kilobyte at &8000+n*&400.  A table
# of anything else would not have that relationship, and would not need
# the &BFEE exception that exists only because block 15's last two bytes
# are where markers 14 and 15 live.
