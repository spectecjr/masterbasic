# Resolving the ROM at boot.

MB &7990 RESOLVE_ROM_ENTRIES

DOC RESOLVE_ROM_ENTRIES
    Find twenty ROM entry points by signature and patch them into the
    code that calls them.

    Called from &75EF and &798D.  Each step is a call to FIND_ROM_CODE
    with six inline bytes -- three opcodes to look for, where to start
    looking, and a signed step -- followed by an LD (nn),HL that drops
    the answer into a patch site.  MasterBASIC therefore contains almost
    no hard-coded ROM addresses.  It knows what the ROM's code looks
    like, not where it is.

    The signatures are ordinary instructions:

        C9 E3 CD    RET : EX (SP),HL : CALL   from &1030, +3
        20 08 78    JR NZ,+8 : LD A,B         from &0370, +2
        3A 40 5B    LD A,(&5B40)              from &2FE0
        7A ED B1    LD A,D : CPIR             from &3000, -4
        21 40 51    LD HL,&5140               from &3080

    Two of the destinations matter more than the rest.  &7DFB and &7E01
    are inside the block at &7BA4 that gets copied into the system page,
    and they are the operand bytes of the JP &0000 instructions in it.
    So the stub's empty jumps are not patched at run time by something
    unknown: they are filled in here, before the block is copied out.
    That is the whole of what was left open about those operands.

    The rest land in this page's own call sites -- &735E, &7468, &757F,
    &7596, &73B4, &73BA, &73BF, V56F6 and others -- so the routine is
    self-patching, and the operands the listing shows at those addresses
    are the shipped zeros rather than what runs.

    The routine that follows it, INSTALL_SYSPAGE_CODE, pokes &18 and &19
    into &594A and &5941.  Those are not opcodes and not part of this
    routine: they are entries 106 and 97 of the ROM's key table, being
    given the codes for word-left and word-right.

MB &799D : two of these results fill the JP &0000 operands in the stub
MB &7AA6 : 24, which the manual gives as the code in "KEY 36+70,24" -- and the INC A below makes the 25 of "KEY 27+70,25"

MB &7AA8 : &594A is KTAB entry 106, the 36+70 of that pair.  IT IS A KEY ASSIGNMENT AND NOT AN OPCODE: this line used to read &18 as JR, which is what the byte would be if it were being executed, and the doc block above the routine says otherwise -- MasterBASIC is doing two KEY statements by writing into the table

MB &7AAC : &5941 is entry 97, the 27+70, and takes the 25

MB &7AB6 : fourteen bytes, which is exactly what the ROM's variable table reserves at PAGER "for paging S.R."

MB &7AC1 : &1D is 29 -- DPVARS and the four XVARs after it, 4 + 9 + 8 + 6 + 2, which is what puts GCM1 at &5A16 and DMPTL at &5A2D

MB &7AC8 : &5896, in the gap between the DEF KEY buffer and KTAB -- &5880 to &58DF is unused, and this takes forty bytes of it

# INSTALLER'S FIRST RESOLVE, which the trace used to mis-align by one
# byte.  Not one of RESOLVE_ROM_ENTRIES's twenty -- those all read
# cleanly.  This is the first of INSTALLER's own seven, at &75F2-&763A.
#
# &75F2 is CD 79 BD, a call to FIND_ROM_CODE, and the trace took the
# first two of those as an inline DEFW, so the whole entry came out as
# instructions that are not there.  The cause was in the sniffer that
# decides how many inline bytes a routine takes: it read straight
# through RESOLVE_ROM_ENTRIES's opening call into that call's own
# signature, whose first bytes C9 E3 decode as RET : EX (SP),HL -- the
# return-address swap it looks for.  It stops at a call now.
#
# Read at the right offset it is the same shape as the twenty below:
#
#     CD 79 BD           CALL FIND_ROM_CODE
#     F5 DF E1 2E 00 FA  signature F5 DF E1 from &2E00, -6
#     22 F0 45           LD (&45F0),HL
#
# and that store is the one notes/mb-romthunks.txt reported missing:
# &45F0 is the SLICING thunk's operand, the only one of the three whose
# patch could not be found.  It was here all along, one byte out.
# The six bytes after the call are its signature block, as they are at
# the twenty below and at the six that follow this one.  Marked data because the trace had already decoded
# them as instructions and only a non-code mark clears those.
MB &75F5-&75FA data
